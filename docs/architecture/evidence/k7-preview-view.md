# K7 的证据：预览视图能否跟住窗口变化、截图替换是否闪烁

对应技术设计 §6.1 末尾的“【未核实】（K7）”和 issue #175。本文自成一体：测量用的脚本是一次性的，没有进仓库，这里保留做法、数字、结论和没有验证的部分。

## 做法

在本机（Apple M3 Max，macOS 27.0.1，Electron 44.5.1）用 `--root` 指向临时目录启动真实的桌面应用，建一个 `html` 项目并运行到就绪，预览视图（`WebContentsView`）摆在界面占位区上。测量脚本在应用启动后驱动窗口：

1. **跟住窗口变化**：连续 20 次用 `setSize` 改窗口宽度，量“调用 `setSize` 到主进程收到界面报来的新占位区矩形（`preview.bounds`）”的时间。矩形由界面的 `ResizeObserver` 实测后经 IPC 报给主进程，主进程随即 `setBounds`。
2. **截帧耗时**：连续 10 次调 `preview.capture`（`webContents.capturePage` 转 PNG 的 data 地址），量往返时间。
3. **截图替换是否看得出差别**：用 `screencapture -l <窗口号>` 截整个窗口三次（实时视图、盖上截图并隐藏视图后、换回视图后），在占位区内每隔 3 个像素取样，比较每个像素的颜色差（三个通道差之和大于 24 算不同）。盖截图的顺序与应用里的 `usePreviewSuspension` 相同：先截帧，截图画出两帧之后才隐藏视图。

## 数字

| 项 | 最小 / 中位数 / 最大（毫秒） |
| --- | --- |
| `setSize` 到收到新矩形 | 2.8 / 7.9 / 15.0 |
| 截帧往返（占位区约 574×638，Retina） | 14.6 / 16.5 / 18.0 |
| 截帧、显示截图、等两帧、隐藏视图的整个过程 | 17.7（一次） |

| 比较 | 不同的取样点 |
| --- | --- |
| 实时视图 对 隐藏视图后显示的截图 | 0 / 157544 |
| 实时视图 对 换回视图后 | 0 / 157544 |

## 结论

- **跟得上**：窗口尺寸变化后，新位置在一帧（60 Hz 是 16.7 毫秒）之内到主进程，最大 15 毫秒。没有测真人拖动窗口边缘的连续事件，也没有测占位区随面板拖动条变化（本 PR 之后才有这些面板）；两者走同一条路径（`ResizeObserver` 到 `setBounds`），预期同样够快，但**没有实测**。
- **截图替换看不出差别**：静态页面上，截图与实时视图逐点一致，换回前后也一致。次序很关键：先让截图画出来再隐藏视图；反过来会露出一帧占位区的底色，所以 `usePreviewSuspension` 在隐藏前等了两帧。
- **没有测**：页面有动画或视频时截图与实时画面的落差（截图是静止的一帧，动画会停在那一帧，属于预期）；多显示器、不同缩放比；窗口被遮住或最小化时 `capturePage` 会失败，主进程把失败当作“没有帧”处理（窗口藏起来时没有浮层可盖，不影响）。
