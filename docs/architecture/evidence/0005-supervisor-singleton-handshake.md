# 0005 的证据：管理进程的单实例、握手和启动方式（K1）

对应决策记录：[0005](../decisions/0005-supervisor-singleton-handshake.md)。本文把技术验证 K1 的实验、数字和采用的算法完整留下来；做实验的临时代码已删除，不再复制。

## 要回答的问题

决策记录 0002 定下“一个管理进程，应用和命令行共用”，并把几件事留给 K1：

1. “监听即是锁”能不能保证从不出现两个管理进程，崩溃留下的残留怎么恢复。
2. 用 Electron 自己的可执行文件“当作 Node 运行”拉起的管理进程，能不能活过应用的退出和强杀，启动多快，macOS 上会不会多出 Dock 图标。
3. Windows 上管理进程能不能活过启动它的终端或程序；别的本地用户能不能连上或冒充它。
4. 纯 JS 在管道抢占和别的用户这件事上能做到什么。
5. 5 秒宽限期、3 秒（正常退出）、10 秒（强杀）这几个时限做不做得到。

## 实验和数字

### A. 同时启动，会不会出现两个管理进程

n 个客户端进程约定同一毫秒开始“连不上就启动”。每轮数：握手拿到的实例号有几种、记录里“正在监听”且进程还活着的管理进程有几个、有没有客户端失败。“残留”= 先起一个管理进程再强杀，留下 socket 文件和发现文件。每个系列 20 轮（最后一个 10 轮）；其中 Electron 系列里的应用是真正的 Electron 进程。每轮走到“我来启动”的进程数等于客户端数，说明竞争确实发生了。

推荐做法（内核锁；Windows 上是管道）出现第二个管理进程的轮数：

| 系列 | 本机 | CI macOS | CI Linux | CI Windows |
| --- | --- | --- | --- | --- |
| 全新，2 个客户端 | 0/20 | 0/20 | 0/20 | 0/20 |
| 全新，8 个客户端 | 0/20 | 0/20 | 0/20 | 0/20 |
| 有残留，2 个客户端 | 0/20 | 0/20 | 0/20 | 0/20 |
| 有残留，8 个客户端 | 0/20 | 0/20 | 0/20 | 0/20 |
| 全新，Electron 应用 + 命令行 | 0/20 | 0/20 | 0/20 | 0/20 |
| 有残留，Electron 应用 + 命令行 | 0/10 | 0/10 | 0/10 | 0/10 |

合计 440 轮，0 轮违规，没有客户端失败。

对照：设计原文的做法（监听失败 → 探测 → 没人应答就删文件重试），只在 macOS、Linux 上有意义：

| 系列 | 本机 | CI macOS | CI Linux |
| --- | --- | --- | --- |
| 全新，2 或 8 个客户端 | 0/40 | 0/40 | 0/40 |
| 有残留，2 个客户端 | 12/20 | 6/20 | 10/20 |
| 有残留，8 个客户端 | 18/20 | 1/20 | 2/20 |

违规的每一轮都是同一个样子：两个管理进程都活着，其中一个监听着已被对方删掉的文件，没有客户端连得上它，也没有人会去停它。

### B. 应用正常退出

| --- | --- | --- | --- | --- |
| 标签页持有的运行停止（上限 3000） | 12 / 34 / 34 | 27 / 38 / 38 | 21 / 32 / 32 | 93 / 166 / 166 |
| 其中 Vite 的 4 轮，最大 | 24 | 36 | 32 | 166 |
| 应用进程退出 | 21 / 40 / 40 | 52 / 80 / 80 | 34 / 42 / 42 | 122 / 213 / 213 |
| 管理进程还在、还能握手 | 10/10 | 10/10 | 10/10 | 10/10 |
| 它确实是 Electron 应用拉起的 | 10/10 | 10/10 | 10/10 | 10/10 |
| 命令行持有的运行还在 | 10/10 | 10/10 | 10/10 | 10/10 |

### C. 应用被强杀

退出改成强杀（macOS、Linux 是 SIGKILL，Windows 是 TerminateProcess）。管理进程发现连接断开，等 5 秒宽限期，再停标签页持有的运行。每台机器 10 轮，其中 4 轮 Vite。

| | 本机 | CI macOS | CI Linux | CI Windows |
| --- | --- | --- | --- | --- |
| 标签页持有的运行停止（上限 10000） | 5025 / 5039 / 5039 | 5041 / 5055 / 5055 | 5019 / 5028 / 5028 | 5072 / 5085 / 5085 |
| 发现连接断开 | 5 / 6 | 11 / 17 | 4 / 8 | 4 / 9 |
| 宽限期结束、开始停止 | 5008 | 5022 | 5009 | 5007 |
| 进程退出 | 5017 | 5030 | 5013 | 5070 |
| 管理进程还在 / 命令行持有的运行还在 | 10/10，10/10 | 10/10，10/10 | 10/10，10/10 | 10/10，10/10 |

时间几乎全是那 5 秒宽限期；发现断开几毫秒，停止在 macOS、Linux 上约 10 毫秒，在 Windows 上约 65 毫秒（`taskkill /T /F`）。

宽限期确实能等到重连：用普通 Node 进程扮演应用，强杀它，2 秒后用同一个客户端标识连回来。强杀后第 8 秒运行还在（四台机器各 3/3）；随后正常道别，运行在 10 到 74 毫秒内停止。

### D. 启动者退出之后管理进程还在不在

macOS、Linux（本机、两台 CI 结果相同），每种 5 轮，启动者分别是普通 Node 和“当作 Node 运行的 Electron”跑的命令行：

| 做法 | 活下来 | 对照：同一个 shell 里没脱钩的后台进程 |
| --- | --- | --- |
| 脚本启动后自己退出 | 10/10 | — |
| 强杀启动它的 shell 的整个进程组 | 10/10 | 10/10 死了 |
| 先向进程组发 SIGHUP，再向管理进程直接发 SIGHUP，再强杀整组 | 10/10 | 10/10 死了 |

活下来之后父进程号都是 1。

Windows（CI），管理进程启动后用 `taskkill /T /F` 结束那个 shell 的整棵进程树，2.5 秒后检查：Windows PowerShell 5.1、PowerShell 7、cmd、Git Bash（普通 Node 跑的命令行）各 3/3；PowerShell、cmd（当作 Node 运行的 Electron 跑的命令行）各 1/1。

Windows 上的 Job Object：一个 PowerShell 进程把自己放进 Job，在里面运行启动脚本，然后被强杀，Job 句柄随之关闭，模拟“把子进程关进关闭即杀分组的终端”。每种 3 轮（第 3 轮 [38179293243](https://github.com/paddychenc75/runyard/actions/runs/38179293243) 和第 4 轮结果相同）：

| Job 的设置 | 启动方式 | 活下来 | 启动到握手（毫秒） |
| --- | --- | --- | --- |
| 没有限制 | 普通（`detached`） | 3/3 | 61 到 70 |
| 关闭即杀（`KILL_ON_JOB_CLOSE`） | 普通 | 0/3 | 63 到 296 |
| 关闭即杀，允许显式脱离（`BREAKAWAY_OK`） | 普通 | 0/3（Node 没有办法在启动时要求脱离） | 60 到 67 |
| 关闭即杀，子进程自动不入组（`SILENT_BREAKAWAY_OK`） | 普通 | 3/3 | 65 到 78 |
| 关闭即杀 | 经 WMI 创建进程（`Win32_Process.Create`） | 3/3 | 446、446、1640（第 3 轮：458、461、665） |

限制：CI 机器在任务结束时清理残留进程，存活只在任务之内量了 2.5 秒；更长时间、关机注销、休眠唤醒都没有测。

### E. 有人抢先占住连接点

一个冒充者进程先在管理进程的连接点上监听并记下收到的每个字节，然后客户端来连。冒充者 4 种行为（不说话 / 回乱码 / 发像样的质询再编一个应答 / 发空 nonce 再把客户端的应答原样发回）× 发现文件 2 种（没有 / 留着带口令的旧文件）× 客户端 2 种（只连接 / 连不上就启动）= 每台机器 16 种情形。事后在冒充者收到的字节里查口令的四种写法（原始字节、base64、base64url、十六进制）。

| | 本机 | CI macOS | CI Linux | CI Windows |
| --- | --- | --- | --- | --- |
| 客户端被骗 | 0/16 | 0/16 | 0/16 | 0/16 |
| 口令出现在冒充者收到的字节里 | 0/16 | 0/16 | 0/16 | 0/16 |
| 没有发现文件时，客户端发出过握手消息 | 0/8 | 0/8 | 0/8 | 0/8 |
| “只连接”的 8 种：报 `SUPERVISOR_UNAVAILABLE` | 8/8 | 8/8 | 8/8 | 8/8 |
| “连不上就启动”的 8 种 | 都连上新起的真管理进程 | 同左 | 7 种连上真的，1 种报 `SUPERVISOR_UNAVAILABLE` | 8 种都报 `SUPERVISOR_UNAVAILABLE` |
| 报错要多久（毫秒） | 约 70；不说话时 4063 | 约 70；4079 | 约 70；4055 | 118 到 134；4108（只连接）、6117 到 6135（先试着启动） |

- 差别是系统造成的：Windows 上管道被别人占着，新管理进程监听失败、自己退出，客户端报错；macOS、Linux 上能在那个目录里建文件的只有本人，新管理进程拿到锁以后把冒充者的 socket 文件换掉。Linux 那 1 种是客户端在新进程监听上之前判了三次失败，再执行一次命令就好。
- 反过来（真的管理进程先在，后来者想在同一个名字上监听）：四台机器上后来者都是 `EADDRINUSE`，真的不受影响。
- 客户端发给冒充者的只有握手消息（810 字节以内），里面是口令的 HMAC 摘要，不是口令。
- 对照：按技术设计 §5.1 原文实现的客户端，冒充者发空 nonce，客户端回 `HMAC(token, "" + clientNonce)`，恰好等于它期待服务端发回的 `HMAC(token, clientNonce)`；冒充者原样发回，客户端验证通过。四台机器都被骗过（口令本身仍然没有泄露）。被骗之后客户端会把请求发给冒充者、相信它的回答。

### F. 另一个系统用户

macOS、Linux（CI，`sudo -u nobody` 运行探测脚本；本机不建用户，只核对权限位：目录 700，socket、发现文件、锁文件 600）：

| 情形 | 连接 | 读发现文件 |
| --- | --- | --- |
| 管理进程建好的样子（目录 700，socket 600） | `EACCES` | `EACCES` |
| 故意把目录改成 755（socket 仍是 600） | `EACCES` | `EACCES` |
| 对照：目录 755，socket 改成 666 | 连上了，收到质询，乱答之后被断开 | `EACCES` |

两台 CI 结果相同。对照那一行证明探测脚本确实连得上，前两行的拒绝是权限起的作用。管理进程启动时先把 umask 设成 077，文件从创建起就是这个权限，没有“先建后改”的空档。

Windows（CI，新建临时普通用户，用它的身份运行同一个探测脚本，之后删除该用户）：

- 连接 `EPERM`，读发现文件 `EPERM`。别的用户用 Node 连不上。
- 管道实际的访问控制表（纯 Node 建管道时不能指定，是系统默认值）：`O:LA D:(A;;FR;;;WD)(A;;FR;;;AN)(A;;FA;;;SY)(A;;FA;;;BA)(A;;FA;;;LA)`，即所有人和匿名登录“只读”，SYSTEM、管理员组、创建者“完全控制”。
- 含义：Node 客户端打开管道后还要设置管道模式，只读权限不够，所以失败；但专门写的本机程序可以只读打开管道，读到管理进程先发的质询（只含一次性随机数和协议版本号），不能写，走不完握手。这是按访问控制表推断的，没有写这样的程序实测。管理员组成员可以完全访问，这在 Windows 上是常态。
- CI 上创建管道的是内置管理员账户；普通用户下默认的访问控制表要在真机上看。

### G. Windows 上的黑窗口

启动选项：启动管理进程 `spawn(execPath, args, { detached: true, stdio: ['ignore', 日志, 日志], windowsHide: true })`；管理进程启动每个运行 `spawn(argv0, rest, { stdio: [...], windowsHide: true })`。管理进程以 `detached` 启动后没有控制台，它再启动控制台程序（node、cmd、Vite）时，不带 `windowsHide` 系统会给每个子进程新开一个控制台窗口，所以必须带。

CI 没有可见的桌面。试过替代指标（子进程有没有窗口句柄、有没有新的 conhost），带和不带 `windowsHide` 看不出差别（窗口句柄都是 0，都有一个 conhost），这个指标没有分辨力，不能当证据。本项标“未验证”。

### H. 残留状态的恢复

强杀管理进程（一半轮次里它还有一个活着的子进程），确认残留在，然后下一个客户端照常“连不上就启动”。

| | 本机 | CI macOS | CI Linux | CI Windows |
| --- | --- | --- | --- | --- |
| 恢复成功 | 20/20 | 20/20 | 20/20 | 10/10 |
| 强杀后留下 socket 文件 / 发现文件 | 20，20 | 20，20 | 20，20 | 不适用，10 |
| 恢复耗时 | 38 / 40 / 40 | 41 / 61 / 63 | 39 / 53 / 54 | 77 / 95 / 95 |
| 被强杀的管理进程留下的子进程还活着 | 10/10 | 10/10 | 10/10 | 5/5 |

macOS、Linux 的 20 轮里内核锁和设计原文的做法各 10 轮：只有一个客户端时两种都能恢复，区别只在并发（实验 A）。最后一行要注意：实验里子进程的输出写进文件，不是写进连着管理进程的管道，而且这个极小的服务平时不输出，所以它没有证实也没有推翻技术设计 §2.4 里“管理进程崩溃后多数开发服务器会自己退出”，只说明不能指望这一点。

### I. 版本不一致（§5.4 的握手表）

四台机器结果相同，每种情形 1 次：

| 情形 | 结果 |
| --- | --- |
| 协议相同 | 直接用，同一个管理进程 |
| 管理进程较旧，没有运行 | 客户端发 `supervisor.shutdown { ifIdle: true }`，旧的退出，客户端启动新的；约 0.2 秒 |
| 管理进程较旧，有运行，仍满足客户端的最低版本 | 兼容使用，带提示 `SUPERVISOR_OLDER_COMPAT`，运行不受影响 |
| 管理进程较旧，有运行，不满足 | `SUPERVISOR_OUTDATED`；旧的管理进程和运行都还在 |
| 管理进程较新，客户端低于它的最低要求 | `CLIENT_OUTDATED`；管理进程不受影响 |
| 管理进程较新，仍愿意服务 | 直接用 |

### J. 测量

启动耗时：从客户端调用 `spawn` 到握手完成，每次用全新状态目录，每种 30 次（毫秒）。

| 管理进程由谁来跑 | 本机 | CI macOS | CI Linux | CI Windows |
| --- | --- | --- | --- | --- |
| 普通 Node | 36 / 37 / 37 | 37 / 55 / 56 | 35 / 51 / 51 | 72 / 87 / 111 |
| 当作 Node 运行的 Electron | 54 / 70 / 70 | 74 / 87 / 90 | 51 / 68 / 69 | 78 / 283 / 667 |

- 管理进程自己的代码从第一行到开始监听只要 1 到 4 毫秒，其余是进程和运行时的启动。
- CI Windows 上 Electron 那一格有一次 667 毫秒的离群值；同一机器类型的第 2 轮运行是 58 / 77 / 113。
- 管理进程已在时，一条命令从头到尾（进程启动 + 连接 + 握手 + 一次请求），中位数 / p95：普通 Node 31 / 33（本机）、37 / 39（CI macOS）、35 / 38（CI Linux）、80 / 88（CI Windows）；当作 Node 运行的 Electron 54 / 56、60 / 64、53 / 59、67 / 76。连接加握手本身 2 到 8 毫秒。这组数字与 K3 的“命令行启动不慢于 150 毫秒”有关，但这里是未打包的 Electron。

空闲内存（启动 3 秒后常驻内存，各 3 次）：

| | 本机 | CI macOS | CI Linux | CI Windows |
| --- | --- | --- | --- | --- |
| 普通 Node | 51 MB | 51 MB | 54 MB | 44 MB |
| 当作 Node 运行的 Electron | 62 MB | 61 MB | 98 到 101 MB | 38 到 41 MB |

macOS 的 Dock 图标：管理进程启动后头 3 秒里每 100 毫秒执行一次 `lsappinfo list`，查它的进程号有没有登记在系统的应用列表里（登记了才有 Dock 图标）。当作 Node 运行的 Electron：本机 3 次、CI 3 次，每次 30 个取样全都没有登记。实验 B、C 里由真正的 Electron 应用拉起的管理进程同样没有登记（每台机器抽查 6 次），而同一时刻那个 Electron 应用本身查得到（类型 `UIElement`），说明这个查法看得见该看见的东西。没有 Dock 图标，也不会跳一下。

socket 路径长度上限（实测）：macOS 104 字节以内可以，107 字节起 `EINVAL`；Linux 108 字节以内可以，120 字节 `EINVAL`。`~/.runyard-dev/run/supervisor.sock` 在本机是 48 字节。主目录很长的用户会碰到。

## 决定与采用的算法

决定见决策记录 0005。总判断：设计成立，不启用“随应用另带独立 Node”的退路，管理进程和命令行保持纯 JS。

### 单实例：内核锁加监听

```
function startSupervisor(stateDir):
  umask(0o077)                                    # 文件从创建起就只有本人可访问
  if platform == win32:
    # 命名管道本身就是锁：libuv 建管道要求“必须是第一个实例”
    server = listen(pipeName)                      # 失败（别人占着）→ 自己退出
  else:
    if macOS:
      fd = open(run/supervisor.lock, O_RDWR|O_CREAT|O_EXLOCK|O_NONBLOCK)
             # O_EXLOCK = 0x20，Node 的 fs.constants 没导出，直接传数值；普通 Node 和 Electron 都实测可用
    if linux:
      lock = listen(抽象命名空间 socket，名字含状态目录的摘要)
    if 拿不到锁: exit(0)                           # 已经有一个了
    # 拿到锁之后，连接点上留着什么都是残留
    unlink(run/supervisor.sock) 忽略不存在
    server = listen(run/supervisor.sock); chmod 600
  写临时文件 → rename 为 run/supervisor.json   # 发现文件，含 token，600
  # 进程死亡时锁由内核释放，不存在“过期的锁”
  # Node 打开文件默认不让子进程继承，所以管理进程的子进程不会替它占着锁
```

Linux 的抽象 socket 没有权限控制，别的用户可以抢这个名字让管理进程起不来（不能冒充、不能连接）。Linux 不是第一版支持的系统，先记着。

### 握手（防冒充）

```
常量: PREFIX = "runyard-handshake-1|"
服务端 → 客户端: challenge { nonce (恰好 32 字节), protocol, minProtocol }
客户端: 若 nonce 长度 ≠ 32 → 断开
        clientNonce = random(32)
        proof_c = HMAC-SHA256(token, PREFIX + "client|" + nonce + clientNonce)
客户端 → 服务端: hello { clientNonce, proof_c, protocol, minProtocol }
服务端: 若 clientNonce 长度 ≠ 32 → 断开；校验 proof_c，不对就断开
        proof_s = HMAC-SHA256(token, PREFIX + "server|" + nonce + clientNonce)
服务端 → 客户端: ready { proof_s, ... }
客户端: 校验 proof_s；不对 → 断开，报 SUPERVISOR_UNAVAILABLE，不发任何请求
# 没有发现文件（没有口令）时客户端根本不发握手消息
# 三条消息的形状永不改变；协议版本和最低版本放在质询和应答里，版本握手表在握手阶段就拿到对方版本
```

### 启动者拉起管理进程（客户端侧）

```
function ensureSupervisor():
  if 读得到发现文件 and 连得上 and 握手通过: return 连接
  # 连接点有人但验证不过 → 报 SUPERVISOR_UNAVAILABLE，不发送口令，可以尝试启动一次
  spawn(execPath, args, { detached: true, windowsHide: true, stdio: ['ignore', 日志, 日志], cwd: 状态目录 })
  # 管理进程需要的一切走命令行参数，不靠环境变量；应用里 execPath 是 Electron，加 ELECTRON_RUN_AS_NODE=1
  # 拿不到锁的新进程自己退出，不会出现第二个
  重试连接直到超时
  # Windows 且启动者在“关闭即杀”的 Job 里：改经 WMI Win32_Process.Create 创建（启动多 0.4 到 1.6 秒）
```

管理进程启动每个运行时一律 `windowsHide: true`，并从子进程环境里去掉 `ELECTRON_RUN_AS_NODE`。

## 后果（细节）

- `platform.ipc.listen()` 在 POSIX 上先拿锁再监听；锁文件 `~/.runyard/run/supervisor.lock`。
- 5 秒宽限期、3 秒和 10 秒两个上限保持不变；实测正常退出后 0.17 秒内停止，强杀后 5.01 到 5.09 秒停止。注意这里的运行很轻：一个停得慢的进程最多再占 3 秒（先礼后兵），5 + 3 仍在 10 秒内，但正常退出时会顶到 3 秒上限。整棵进程树怎么停见决策记录 0006。
- 管理进程被强杀后它的子进程可能一直活着（实测输出写文件的子进程全部仍在运行），下次启动时按记录核对身份并清理必须做。
- 已知空白：发现文件被删掉而管理进程还活着时，客户端没有口令，会一直报 `SUPERVISOR_UNAVAILABLE`，直到管理进程空闲退出；没测，也没有设计对策。

## 已接受的风险

1. Windows 命名管道的默认访问控制表允许所有人只读打开，纯 Node 无法修改。已接受，理由：Runyard 面向单用户的开发者电脑；口令不会在管道上明文传输（握手只发 HMAC 摘要），发现文件只有本人可读；别的用户即使只读打开，也只能读到一次性随机数和协议版本，走不完握手；要修好必须用原生模块，会破坏“管理进程和命令行不含原生模块”这条规则，而握手已经挡住了冒充和越权。
2. 别人先占住管道名会让管理进程起不来（功能不可用，不泄露东西）；Linux 抽象 socket 同理。
3. 管理员组成员在 Windows 上可以完全访问管道，这是系统常态。

## 没有验证的

- 从打包后的应用拉起管理进程（K3，决策记录 0007）；经 WMI 启动“当作 Node 运行的 Electron”（WMI 只用普通 Node 测了，Electron 需要的环境变量要另想办法传）。
- Windows 真机的全部项目（下一节）。
- 管理进程存活超过几秒之后：注销、关机、休眠唤醒、快速用户切换。
- 别的用户用专门写的程序只读打开 Windows 管道（按访问控制表推断可以，没有实测）。
- 发现文件被删而管理进程活着（见上）。
- x64 的 Mac、arm64 的 Windows。
- 停得慢的运行、输出走管道的运行（K2、M1）。

## 需要在负责人的 Windows 真机上复核

以普通用户登录，装好 Node 24：

1. 分别从 Claude Code、VS Code 的终端、Windows Terminal、Git Bash 启动管理进程，记下进程号；关掉那个终端（或退出那个程序）；在另一个终端里查询，仍是同一个进程号 = 活下来了。哪一处活不下来，就在那一处改用 WMI 创建方式再试。（预览版发布前必须做：Job Object 关闭即杀有真实风险。）
2. 上面每次启动时盯着屏幕：有没有黑窗口闪一下；再启动一个运行，看起运行时有没有。（预览版发布前。）
3. 另建一个普通用户登录，对同一个管道名运行探测脚本，期望连接不成功。（可以更晚。）
4. 普通用户下管道的访问控制表，看与 CI 上的是否一致。（可以更晚。）
5. 打包后的应用拉起管理进程后，退出应用、在任务管理器里结束应用，各看一次管理进程是否还在（与 K3 一起做；预览版发布前）。
6. 实时防护开着时，启动到握手的耗时。（可以更晚。）

## 实验中踩到的坑

- Electron 主进程入口是 ES 模块时，顶层 `await app.whenReady()` 会互相等待，应用永远不就绪。退出流程里“先道别再退出”要防止第二次 `app.quit()` 绕过等待。
- `electron@44.4.5` 这个 npm 包没有安装脚本，二进制在第一次使用时才下载（或手动执行安装），CI 里要显式下载一步；根目录 `allowBuilds` 里的 `electron` 一项对这个版本不起作用。
- 实验的清理程序最初按“命令行里出现本次随机标记”找残留进程并强杀，杀掉了开发者自己用来查看临时目录的 shell。教训：清理按标记和路径同时匹配，别的只列出不碰（K2 的 Windows 事故见决策记录 0006）。
- 实验依赖：测量用的 Vite 7.3.6 带来的间接依赖有一条高危公告，修复版本还不满 14 天，所以测完后拿掉；Vite 的那几轮（实验 B、C 每台机器各 4 轮）数字来自拿掉之前的运行。教训：加依赖时间接依赖的公告也要查，`pnpm deps:lookup` 只查直接依赖。
