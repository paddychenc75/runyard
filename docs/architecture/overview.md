# 架构总览

一页讲清进程和包。这是骨架：只写已经定下来的结构，细节在技术设计（`docs/product/03-tech-design.md`）里，每个包开工前再把它需要的细节转写到这里和它自己的 `AGENTS.md`。为什么这样做，看 [决策记录](decisions/)。

## 进程

| 进程 | 活多久 | 负责 |
| --- | --- | --- |
| 桌面应用主进程（main） | 随应用 | 窗口与预览视图、替界面转发请求。不启动用户代码，不写共享的状态文件 |
| 界面进程（renderer） | 随窗口 | 界面。不能用 Node 接口和文件系统 |
| 终端进程（pty-host）、文件进程（fs-host） | 用到时启动 | 终端；项目内文件读写和监听 |
| 预览（preview） | 每个有页面的标签页一个 | 加载本机开发服务器的页面，没有 Node |
| 管理进程（`runyardd`，代码里叫 supervisor） | 谁先需要谁启动；没有连接也没有运行满 60 秒后自己退出 | 一切“运行”，以及所有共享文件的写入。纯 Node，不依赖 Electron。单实例：Windows 上命名管道本身是锁，macOS 和 Linux 上另加内核锁 `run/supervisor.lock`；握手是防冒充的双向质询（决策记录 0005） |
| 命令行（`runyard`） | 一条命令 | 连接管理进程、发请求、打印结果 |

桌面应用和命令行都是管理进程的客户端，经同一个本地 socket（Windows 上是命名管道）说同一套协议，一行一个 JSON。所以命令行启动的运行在应用里看得见，应用退出后管理进程还能继续照看。出处：技术设计 §2.1 到 §2.4。

运行的输出走管道，不走伪终端：日志存未清洗的整行，读取时清洗（决策记录 0008）。停止一次运行按系统分别做：macOS 整个进程组，Windows 先核对进程号和创建时间再 `taskkill`（0006）。工具环境由管理进程按登录加交互的 shell 解析，带缓存和后台刷新，界面不等待（0009）。Windows 上有一个随包的辅助程序（暂定名 `runyard-helper.exe`，回收站操作，可选的 Job Object 函数），只随桌面应用，不是 Node 模块（0006、0010）。

## 包

依赖方向的唯一出处是 `tooling/checks/layers.json`，根 `AGENTS.md` 里的依赖表由它生成。下表只说每个包是什么；“现状”以根 `AGENTS.md` 的生成表为准。

| 包 | 职责 | 第一次出现 |
| --- | --- | --- |
| `@runyard/protocol` | 所有跨进程约定：消息、事件、错误码、各种文件的格式定义 | 已有（占位），M1 写实 |
| `@runyard/platform` | 系统差异的唯一出口，每个系统一份实现 | M1 |
| `@runyard/core` | 工具检测、运行引擎、资源库、模板、自动清理的判断 | M1 |
| `@runyard/supervisor` | 管理进程：socket 服务、会话与持有者、空闲停止 | M1 |
| `@runyard/client` | 连接管理进程的客户端，命令行和桌面主进程共用 | M1 |
| `runyard`（命令行） | 命令解析和输出 | M1 |
| `@runyard/i18n` | 给人看的文字、格式化、语言解析 | M1（精简版），M2 补界面一侧 |
| `@runyard/testing` | 测试用的假进程、假时钟、假平台 | M1 |
| `@runyard/tokens`、`@runyard/ui` | 设计变量；通用界面组件（不认识产品） | M2 |
| 桌面应用、网站 | Electron 应用；介绍和下载站 | M2；M4 |

出处：技术设计 §3.1、§3.2、§11.2。

## 三条贯穿全局的规则

1. **所有共享文件只由管理进程写。** 应用和命令行都经协议请求它，不直接写状态文件（技术设计 §2.3）。
2. **系统差异只在平台层。** 启动和结束进程、路径、端口、废纸篓（macOS 优先 `/usr/bin/trash`，Windows 用随包辅助程序加预检，绝不退到永久删除，0010）、找工具，全部收进 `@runyard/platform`；其他代码不判断系统（技术设计 §3.2 规则 4、§7.1）。
3. **管理进程一侧不产生给人看的句子。** 只发“错误码加参数”，界面和命令行各自按当前语言拼成句子（技术设计 §3.2 规则 7、§5.1）。

## 规则怎么强制

每条结构规则至少有一个会让 `pnpm check` 或类型检查变红的机制：pnpm 的严格依赖、TypeScript 的 project references、各包不同的类型环境、Biome 的导入规则、`tooling/checks/` 里的检查脚本。清单见技术设计 §3.3 和 §9.4；现在已有哪些，看 `tooling/checks/run.ts`。
