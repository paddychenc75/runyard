# 0002. 所有运行由一个独立的管理进程统一管

状态：已接受

日期：2026-10-12

来源：PRD #prd-run-ownership；技术设计 §2.1 到 §2.4

## 背景

PRD 要求命令行（包括智能体）启动的运行在应用退出后继续，由后台照看。应用和命令行还要改同一批状态文件；调研实测过两个写入方会把 JSON 写坏。界面和命令行如果各自实现一套运行逻辑，两套会各自走样。

## 决定

设一个后台程序 `runyardd`（代码里叫 supervisor），所有“运行”和所有共享文件的写入都由它做。桌面应用和命令行都只是它的客户端，经同一个本地 socket（Windows 上是命名管道）说同一套协议，一行一个 JSON。它是纯 Node 程序，不依赖 Electron，不含需要编译的模块。谁先需要谁启动它，启动后与启动者脱钩；没有连接也没有运行满 60 秒后自己退出。

## 后果

- 桌面主进程不启动用户代码，不写共享的状态文件；命令行不直接写状态文件。
- 标签页持有的运行在标签页关闭、应用退出或应用崩溃（连接断开 5 秒后）时停止；命令行持有的运行继续，空闲后自动停止。
- 管理进程自己崩溃后不做“重新接管”：下次启动按记录核对身份，还活着的整棵结束，标为“已崩溃”。
- 应用里用 Electron 自己的可执行文件“当作 Node 运行”来启动它，所以打包时必须保留这项能力。
- 应用、命令行、管理进程的版本可能不一致，靠连接时的版本握手处理（技术设计 §5.4）。
- 还没验证的部分：启动耗时、macOS 上是否多出 Dock 图标、Windows 上能否活过启动者。这些是技术验证 K1、K3 的内容；不成立时的退路是随应用另带一个独立的 Node 程序。验证结论出来后新写一份决策记录。

## 被否的方案

- 把运行放在 Electron 主进程里：应用一退，运行就没了，做不到 PRD 的要求。
- 用本机 HTTP 端口做传输：任何网页都能访问本机端口，要额外防跨站请求。
- 应用和命令行各自直接读写状态文件：两个写入方会把文件写坏。
