# 0008. 运行输出走管道，日志存未清洗的整行、读取时清洗

状态：已接受

日期：2026-10-12

来源：技术设计 §4.5、§7.2 第 13 行、§11.1 K4、附录 A 第 1 行；证据见 [evidence/0008](../evidence/0008-log-capture-and-cleaning.md)

## 背景

附录 A 第 1 行裁决运行输出走管道、不用伪终端，代价是 Windows 上输出可能带控制字符、中文乱码、被整块延迟。K4 在 GitHub 运行器（`windows-2025`、`macos-26`、`ubuntu-latest`）上用 Vite 8.3.1、Next 16.3.6、Node+TS、Python 3.12 和 3.14、uv、Go 1.26、pnpm 11 实测（运行 38165029567，PR #2）：
- Vite、Next 的报错代码框自带颜色，环境变量和参数都去不掉（Vite 剩 68 个、Next 剩 26 个颜色码）；
- Python 在 cp1252 下写中文直接崩溃（3 个入口各 3 次全崩），默认还把输出攒成整块（6004 ms 一批，强杀时 0/5 行）；Node、Go 无此问题；
- 真实中文 Windows 11（代码页 936）没有测，GBK 只做了模拟。

## 决定

继续走管道。日志存未清洗的整行（只切行和解码，控制序列原样保留），`runyard logs` 和界面的纯文本由九步清洗规则生成（规则全文在证据文档 6.2）：按 0x0A 切行、去行尾 CR、先严格 UTF-8 再 GB18030、去 BOM、剥各类转义序列、行内回车只留最后一段、删剩余控制字符、纯控制序列的行丢弃。所有系统给运行加 `PYTHONUTF8=1`、`PYTHONUNBUFFERED=1`、`NEXT_TELEMETRY_DISABLED=1`，颜色沿用“强制颜色”；不设 `CI=1`。

## 后果

- 落盘形状：磁盘上的日志按 `LogEntry` 一行一个 JSON，`text` 必须是字符串，所以切行和解码放在写入时，其余各步放在读取时；结果与“全部在读取时清洗”等价，但字节本身不另存。这是对“存原始字节”的一处小偏离；若以后需要重新按别的编码解码，再加存字节的字段。
- 清洗规则是 `@runyard/core` 里一个带测试的函数，用 K4 的 18 条自检和 2 万行批量用例作测试数据。
- 运行器环境变量表加 `PYTHONUNBUFFERED=1`，`PYTHONUTF8=1` 不再只给 Windows；模板说明写明 Vite、Next 的错误代码框颜色去不掉、`--no-color` 不可用（会报错退出）。
- `pnpm install` 不用 `--reporter=silent`。
- 两路输出按到达顺序合并，紧凑写入时跨管道会倒序（400 行紧凑写入 75 到 200 次），文档不承诺 stdout 与 stderr 的严格先后。
- 多行重画（`ESC[1A` 加 `ESC[2K`）无法还原，只留每个状态。
- 在负责人的中文 Windows 11 真机上复核代码页 936 的编码，列入预览版发布前的真机清单。
- 判定保持原样：“没有控制字符残留”在读取时清洗的条件下通过；“中文不乱码”有条件通过；“不被整块延迟”只有加 `PYTHONUNBUFFERED=1` 后 Python 才通过。

## 被否的方案

- 伪终端：要把 node-pty 带进管理进程和命令行，破坏纯 JS 规则，且 Windows 的伪终端会改写输出（附录 A 第 1 行）。
- 只靠 `NO_COLOR` 让日志干净：Vite、Next 的原生报错框不认，实测仍剩颜色码。
- 只在 Windows 上加 `PYTHONUTF8`：缓冲问题在三个系统上都存在，统一加更简单。
- 写入时就清洗、只存纯文本：丢掉颜色，界面无法再显示彩色输出。
