# 0006. 停止运行：进程组和 taskkill，输出仍走管道

状态：已接受

日期：2026-10-12

来源：技术设计 §4.3、§4.4、§7.2 第 2、3 行和表后“Job Object 辅助程序的形态”、§11.1 K2 行、附录 A 第 1 行；证据与算法见 [evidence/0006-stop-process-tree.md](../evidence/0006-stop-process-tree.md)

## 背景

运行的输出用管道接收，不用伪终端（附录 A 第 1 行）。这条裁决当时留下三件没核实的事：整棵进程树停不停得干净、端口多久能重新绑定、强制结束会不会留下坏的锁文件让下一次启动失败。技术验证 K2 在负责人的 Mac 和 GitHub 的 `macos-26`、`windows-2025`（Windows Server）、`ubuntu-latest` 上，对八个运行器各起停 50 次，另做了请求进行中、启动中途、安装中途停止，把这三件事量了出来（PR #4，最终数据 CI 运行 38172582221）。

## 决定

维持“输出走管道”，不重开伪终端。停止算法按系统：

- macOS：每次运行自成进程组，整组发终止信号（Go 的运行器发中断信号），等 `graceMs`，再整组强制结束。
- Windows 第一版：先核对根进程的 pid 和创建时间，再 `taskkill /PID <pid> /T /F`，等 exit 事件，再试绑端口复查。
- `runyard-job.exe`（Job Object 辅助程序）第一版停止不需要，不做；它和文件操作所需的 Windows 辅助程序合并为同一个可执行文件（0010），在 Windows 预览版里一起做。

## 后果

- 只等进程的 exit 事件，不等输出管道的 close；确认停止后主动销毁管道。
- `graceMs` 默认 2000，不是 3000：升级为强制结束时停止会拖到 `graceMs` 之后，3000 顶到“3 秒内端口可重绑”的线。
- **Windows 上结束任何进程之前，必须同时核对 pid 和创建时间。** 原因：pid 在父进程死后不变且很快被复用；K2 的测试程序只凭父进程号认后代，把 `csrss.exe`、`winlogon.exe` 等系统进程当残留结束，弄坏了一台一次性的 CI 虚拟机。
- 每次运行的环境变量带运行标记；改名、删除之前在全机找带标记的进程，等它们走掉（上限 2 秒）。Next 退出时另起的脱离进程组的遥测进程最长活 0.95 秒。
- Go：macOS 用中断信号；管理进程给每次运行单独设 `GOTMPDIR` 并在停止后删除（否则 `go run` 每次被结束都留一个 `go-build*` 目录）。
- 运行器直接用 `node` 跑入口文件：Windows 上 `pnpm exec vite` 是 4 层进程，直接跑是 1 层。
- 管理进程崩溃后不能指望子进程自己退出，下次启动按记录核对身份并清理是必须的。
- 若以后做辅助程序：创建进程时就指定 Job；停止走标准输入指令；发 Ctrl+C 前自己开控制台并清掉继承来的“忽略 Ctrl+C”。
- 接受的局限：Windows 的数字只来自 Windows Server 2025 的 CI 机器（管理员账户），发预览版前要在真机上以普通用户复核。

## 被否的方案

- 运行改走伪终端：强制结束没有弄坏任何运行器的项目，原生模块进管理进程的代价换不回收益；辅助程序在管道下也能发 Ctrl+C。
- 第一版就做 `runyard-job.exe`：`taskkill` 已满足三条标准；未签名 exe 会不会被杀毒软件拦还没看（K14）。
- macOS 上停止后按工作目录补杀：1800 次停止没有一次需要；只保留“改名前等带标记的进程走掉”。
- 只凭父进程号找后代来清理残留：pid 复用时会认错并杀到无关进程。
