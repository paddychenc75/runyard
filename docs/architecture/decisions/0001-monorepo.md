# 0001. 一个仓库放全部东西（monorepo）

状态：已接受

日期：2026-10-12

来源：技术设计 §1 第 1 条、§3.1、§3.2、§12“由技术负责人直接决定的事项”、附录 A 第 7 行

## 背景

Runyard 有桌面应用、命令行、管理进程、网站、内置模板和文档。它们共用同一套协议、同一份文件格式定义、同一个版本号，代码主要由智能体写。需要让一次改动能同时改到协议的两端，并且让“谁可以导入谁”能被机器检查。

## 决定

所有东西放在一个仓库里，用 pnpm 工作区加 Turborepo 管理。划分为十个包（protocol、tokens、i18n、ui、platform、core、supervisor、client、cli、testing），外加桌面应用和网站两个应用；内置模板是纯数据，不是包。包之间允许的依赖方向只有一个出处：`tooling/checks/layers.json`。全仓库一个版本号。

## 后果

- 每个包都要付出固定成本：自己的 `AGENTS.md`、配置、在 `layers.json` 里登记。所以不轻易加包。
- 依赖方向由多道机制强制，都不依赖 TypeScript 的版本：pnpm 的严格依赖、`tsc -b` 的 project references、各包不同的类型环境、Biome 的导入规则、`layers` 检查。
- 增删一个包或改依赖规则，要改 `layers.json` 并新写一份决策记录。
- 包按里程碑逐个建，不提前建空包；目录位置从一开始就定好（技术设计 §3.1）。

## 被否的方案

- 分得更细（把格式定义、工具检测、运行引擎、资源库各做成一个包）：每个包都有说明文件、配置和登记的成本；改为把工具检测、运行引擎、资源库做成 core 的三个子目录，并检查它们之间的方向。
- 让桌面主进程直接导入 core：与“所有共享文件只由管理进程写”冲突，主进程经协议调用即可（附录 A 第 10 行）。
