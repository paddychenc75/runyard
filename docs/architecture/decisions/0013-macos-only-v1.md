# 0013. 第一版只做 macOS，为以后支持 Windows 留好工程结构

状态：已接受

日期：2026-10-12

来源：技术设计 §7.1、§7.6、§12 第 47 项；PRD #prd-release-plan；负责人 2026-10-12 的决定

## 背景

范围的变化经过三步：最初的 PRD 是 macOS 为正式版、Windows 为预览版；2026-10-11 负责人选了方案 B（两个系统从第一次提交起同时构建和测试，Windows 桌面版晚一个里程碑以预览版发布，决策记录 0003 据此写成）；2026-10-12 M0a 技术验证做完后，负责人改了：“这一版还是只做 mac，但是工程上要做好工程化，后续需要容易且方便拓展 Windows 支持”。方案 B 的 Windows 增量被设计估计为约 25% 到 35%（没有测量过的基数），其中大半是第二份平台实现、辅助程序、安装器和界面适配。

## 决定

第一版只发 macOS。Windows 完全不在第一版里：没有预览版，没有 Windows 的命令行发布、安装器、辅助可执行文件，也没有 Windows 专属的产品工作。同时工程上保留“以后加 Windows 又容易又便宜”所需的、现在做便宜以后补贵的部分。

保留：

1. 平台层：所有系统相关的行为（启动进程、停止进程树、本机通信端点和锁、环境与工具链解析、废纸篓、路径、端口、打开文件管理器、终端、编辑器、链接协议、通知）仍在 `@runyard/platform` 的接口后面；“`platform` 包之外不读 `process.platform`”仍由 `platform-branching` 检查强制，`platform-contract` 检查仍在 M1 加入。接口按 0005 到 0010 里的 Windows 实测来设计：方法签名不假设 POSIX（接口里没有信号和进程组，进程身份是 pid 加启动时间，有 `PATH_LOCKED`，废纸篓可以失败而不是退到永久删除，通信端点是不透明的地址）。只写并发布 `darwin` 实现；薄 `linux` 实现照旧（契约测试在两个系统上跑）；`win32` 实现现在不写，接口、契约测试和决策记录就是以后 Windows 实现要接上的东西。
2. 不花钱的可移植写法：运行器命令是不经 shell 的参数数组；服务只绑定和探测 `127.0.0.1`；项目名在所有系统上都拒绝 Windows 保留名和末尾的点、空格；路径用路径工具拼，不手写 `/`；文本文件用 LF；核心、管理进程、客户端、命令行保持纯 JS、无原生模块、不导入 Electron；核心包不产生给人看的句子；随系统变的用词走 i18n 的平台选择机制（只填 macOS 一支）。
3. CI：`windows-2025` 的 test 任务留在必过检查里，只跑与平台实现无关的部分（仓库检查、`protocol`、`i18n`，以及测试不需要平台实现的包），用来尽早发现路径分隔符、换行和大小写敏感的错误。依赖平台实现的测试（核心运行引擎、`supervisor`、`client`、命令行集成、模板）只在 macOS 和 Ubuntu 上跑，在 Windows 上通过唯一一个有文档的机制跳过（测试标签或项目级条件，名字写进测试手册），不在测试里零散写 `if (process.platform …)`。工作流文件现在不改。
4. 知识保留：0005 到 0010 及其证据里的 Windows 结论原样保留；“以后做 Windows 要做什么”的有序清单写在[证据文档](../evidence/0013-macos-only-v1.md)的附录 A，M1 规格里因此退役的 Windows 场景原文放在附录 B。

推迟（移到“Windows（以后）”）：`win32` 平台实现、Windows 辅助程序、NSIS 安装器和钩子、Windows 命令行启动脚本、Windows 界面适配和 tokens、Windows 工具安装提示、Windows 速度目标、MW 里程碑、发布计划里的“Windows 11 预览版”、20 项真机验证（清单保留，负责人的 Windows 电脑第一版用不上）、Windows arm64 与 x64 发布目标、M0b 里只属于 Windows 的部分，以及技术设计 §12 里只涉及 Windows 的负责人决定（回答保留，作为以后的输入，不是第一版的规则）。

## 后果

- 取代方案 B，也就取代 0003 里“macOS、Windows 各一份实现、Windows 自动测试必须通过”的部分；0003 的其余规则由本记录沿用，所以 0003 标为已被取代。0005 到 0010 的决定对 macOS 仍然有效，其中的 Windows 条目是以后的输入，不是第一版要做的事；这些记录不改写。
- 诚实的代价：只有一个发布的实现，接口比有两个实现的更少被检验。缓解：接口按 M0a 的 Windows 实测来定；薄 `linux` 实现和契约测试让接口在第二个系统上跑；Windows 任务继续检查中立代码。残留风险：第一个 Windows 实现仍可能要求改接口。
- 发布计划、里程碑、验收标准、下载页、CI 的矩阵里不再有 Windows 条目；M1 议题里纯 Windows 的移出里程碑，混合的删去 Windows 部分。
- 第一版代码里不许新增 Windows 专属代码（含 `win32` 目录、辅助程序源码、安装器配置）。
- 工作量：第一版去掉了设计里算给 Windows 的那一块增量；剩下的数字仍是没有测量过的估计。

## 被否的方案

- 方案 B（两个系统同时构建和测试，Windows 预览版晚一步）：2026-10-11 选的，2026-10-12 被负责人改掉，Windows 增量不值得放进第一版。
- 完全不为 Windows 留结构（原来的方案 C）：接口会不知不觉带上 POSIX 假设，以后补要改核心。
- 现在就写 `win32` 的平台实现但不发布：仍要付出大部分成本，而且没有真机验证的实现是未经检验的代码。
- 把 Windows 任务从 CI 里整个拿掉：它免费、已经绿，能早早发现路径、换行和大小写错误。
