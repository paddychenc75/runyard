# 0003. 系统差异全部收进平台层

状态：已被 0013 取代

日期：2026-10-12

来源：技术设计 §1 第 4 条、§3.2 规则 4 和规则 6、§3.3、§7.1、附录 A 第 2、3、6、9、17 行

## 背景

Runyard 的核心是启动、看管、停止别人的进程和管理文件夹。这一层 Electron 不帮忙，macOS 和 Windows 几乎处处不同：启动和结束进程、路径、端口、废纸篓和回收站、找工具。负责人决定两个系统同时构建和测试（方案 B）。如果各处代码自己判断系统，差异会散落全仓库，Windows 的问题只能事后逐个找。

## 决定

凡是因系统而异的行为，全部收进一个包 `@runyard/platform`：一个接口，macOS、Windows 各一份实现，Linux 一份薄实现（只为让测试在三个系统上跑，不是支持的系统）。业务代码只调用这个接口。系统分支（读 `process.platform`、直接启动进程、手写路径分隔符）只许出现在平台层，以及桌面应用主进程里专放依赖 Electron 的系统差异的 integration 目录。

## 后果

- 平台层从第一次实现起就有 macOS 和 Windows 两份，Windows 的自动测试必须通过。
- 接口的每个成员都要有契约测试，同一组测试对每个实现各跑一遍（`platform-contract` 检查，随平台层加入）。
- 允许的两处之外出现系统分支，由 `platform-branching` 检查拦住（随平台层加入）。
- 平台层不含原生模块：`packages/` 下只用纯 JavaScript 的第三方库。唯一的原生模块 node-pty 只在桌面应用的终端进程里。
- 删除用户的项目只有平台层的 `fs.trash` 一条路；Linux 上这一组抛“不支持”。
- 加一个因系统而异的行为：在接口上加方法，每个系统各写一个实现，补契约测试，其他包只调接口。

## 被否的方案

- 把伪终端（pty）做成平台层的一项服务：会把 node-pty 带进管理进程和命令行，破坏“纯 JavaScript”。
- 用原生模块做文件监听并放进平台层：管理进程自己也要监听，必须是纯 JavaScript，所以用 chokidar。
- 用 ESLint 的边界插件来拦系统分支：改用 Biome 加检查脚本，一个工具，不随 TypeScript 版本变。
- 不做 Linux 实现：契约测试和管理进程的集成测试就不能在三个系统上跑，Ubuntu 上的检查会红，接着被改成跳过。
