# 0012. 变更只经 pull request 进入 main，检查通过即自动合并

状态：已接受

日期：2026-10-12

来源：技术设计 §8.3、§8.4、§11.3、§12“由技术负责人直接决定的事项”；负责人 2026-10-12 的决定

## 背景

仓库的代码主要由智能体写，负责人一个人维护，没有第二个评审人。要求“别人批准”的规则在这里没有人可以满足；但让智能体直接推送到 `main`，检查就只是建议。负责人要把关的是“做什么”（行为），不是“每一行怎么写”。

## 决定

`main` 只接受经 pull request 进来的变更。PR 通过六项必过检查后自动合并，负责人在合并之后再看。会改变行为的改动，在规格阶段先由负责人同意。`main` 由规则集保护：

- 必过检查六项：`lint`（格式、仓库检查、标题格式）一项；`test` 三项（`ubuntu-latest`、`macos-26`、`windows-2025`）；审计闸门；依赖变更审查。
- 不许强制推送、不许删除 `main`、要求线性历史；没有任何可以绕过的人或应用。
- 只许 squash 合并，进入 `main` 的提交信息来自 PR 标题。
- 不要求批准性评审（`required_approving_review_count` 为 0），因为负责人是唯一的维护者。

## 后果

- 技术设计 §8.3、§8.4、§11.3 和 `CONTRIBUTING.md` 按这个流程写；PR 标题格式由 `check-title` 在 `lint` 里检查。
- 检查没过就不会合并：修好再推，不绕过、不改规则让它变绿（根 `AGENTS.md`“禁止事项”不变）。
- 合并之后的评审是事后的：发现问题用新的 PR 改，不改写历史。
- 把关点前移到规格：行为变化必须在写代码前得到负责人同意，否则自动合并会把未经同意的行为放进 `main`。
- 规则集的设置在 GitHub 仓库里，不在代码里；改它要负责人操作，改动要记在这份记录的后继记录里。

## 被否的方案

- 要求一位评审人批准：只有一个维护者，无人可批；开个“自己批自己”的例外等于没有规则。
- 允许负责人绕过规则集直接推送：绕过是一种例外，会被习惯性地使用；确实需要时再临时改规则集。
- 合并方式开放 merge 和 rebase：进入 `main` 的信息要来自 PR 标题，这样标题格式检查才有意义，更新日志才干净。
