<a id="prd-product"></a>
## 1. 产品

Runyard 是一款开源桌面应用，用来管理 demo 并快速运行。选一个模板，约一秒后
项目就跑起来；在类似 VS Code 的编辑器里修改，结果实时可见；之后能在资源库里
再找到它。它用本机已有的工具链运行代码，每个项目都是普通文件夹，并通过 CLI
向 AI 智能体提供同样的操作。

与调研中发现的工具相比，**它的差异在于**：工程化的本地模板、秒级创建、
让小项目有处安放的资源库，以及面向服务类项目的内置请求面板（同类产品都
没有）。把“本地模板、资源库、运行”三者合在一起的产品目前没有查到。

需要清醒看待的两点：给智能体用的命令行已经不算独特，很多工具都有；最接近
的对手是 lpm，它已经签名发布、有命令行，只差模板和创建功能，而且更新很快。
进程启动器和端口查看器已经很多，不是本产品要竞争的方向。

<a id="prd-create"></a>
### 4.1 创建

<a id="prd-template-picker"></a>
- P0：`⌘N`（Windows 上是 `Ctrl+N`）打开模板选择器，焦点落在搜索框；默认视图的顶部是“最近使用”分组，
  其后才是按类型的分组；选定模板后按 Enter 进入下一步。
<a id="prd-create-dialog"></a>
- P0：**选好模板后弹出“新建项目”弹窗**（负责人 2026-10-11 在设计稿上确定，
  取代此前“不询问名称、回车即建”的做法）。弹窗里有三项：
  <a id="prd-naming"></a>
  - **名称**：已自动填好“模板标识加序号”（如 `react19-1`、`react19-2`），
    打开时全选，可以直接用，也可以改。序号取现有同名项目中最大的序号加一，
    不回头补空缺（现有 `react19-1` 和 `react19-3`，下一个是 `react19-4`）。
    名称既是显示名也是文件夹名，放在资源库根目录（`~/Runyard`；Windows 上在 `%USERPROFILE%` 下，资源库在 OneDrive 等同步目录下时给警告）下；
    与现有项目重名时，名称下显示行内错误“这个名字已被占用”，不能创建。名称的合法字符见 §9 第 6 项：
    小写字母、数字、连字符，最长 64 个字符，另外不能是 Windows 保留名（`con`、`nul`、`com1` 等），
    所有系统都禁止，这样资源库能搬到 Windows。
  - **备注**：可选。
  - **自动清理**：可选，默认关闭（弹窗默认状态下，天数选择收起）。打开后选择
    多久没打开就清理（7 天、30 天、90 天或自定义）。
  三项都有默认值，直接按 Enter 就创建并运行，所以想快的时候仍然只是多按
  一次回车。在备注里用输入法时，Enter 是确认候选词，不触发创建。
<a id="prd-note"></a>
- P0：**备注**（负责人 2026-10-11 在设计稿上提出）。创建时可以顺手写一句
  备注，说明这个 demo 是做什么的；可以不填，不影响“回车即建”。备注显示在
  资源库里名称的下方，可随时修改，搜索时也会匹配备注。命令行对应
  `--note "……"`，智能体创建项目时应当填写。自动清理对应
  `--clean-after 30d`，不带这个参数就是已保留。
- P0：工作区立即打开。预览面板依次显示复制、安装、启动、就绪，并附带实时
  日志行，直到结果出现。
<a id="prd-missing-runtime-prompt"></a>
- P0：**缺少运行环境只在用到时提醒**（负责人，2026-10-11）。用户选定某个
  模板创建项目、或打开已有项目时，才检查这个项目需要的工具；用不到的
  语言缺不缺，一律不打扰。
<a id="prd-failure-states"></a>
- P0：**运行失败不会导致创建失败，项目始终保持可编辑。** 下面六种情况，
  各自在预览区有明确的画面：说明原因、给出下一步操作。表末两行是文件占用和路径过长的提醒，
  主要出现在 Windows 上。

  | 情况 | 预览区写明 | 操作 |
  | --- | --- | --- |
  | 缺少运行环境 | 缺哪个工具、需要什么版本、当前是什么版本（版本过低时同样写明），以及当前系统的安装命令 | 复制命令、在终端中运行、重新检测；“已经装了？指定路径…” |
  | 依赖安装失败 | 启动清单停在“安装”，标红，显示输出的最后几行 | 重试、查看输出；镜像源或代理有问题时给“去设置检查” |
  | 离线且依赖未缓存 | “离线：N 个包未缓存” | 重试、去设置检查镜像源和代理；编辑照常可用 |
  | 端口被占用 | 不算失败：自动改用下一个空闲端口并启动，预览区上方说明原端口被谁占用、现在用的端口；原端口被 Windows 保留时没有占用者，写“被 Windows 保留” | 知道了；要保持原端口时，先停止占用者再重启 |
  | 启动超时 | 30 秒仍未就绪时保持“启动中（较慢）”并显示日志；进程退出才算失败 | 停止、查看输出 |
  | 运行中崩溃 | 保留最后一帧并盖一层提示，写明退出原因 | 重新运行、查看输出 |
| 文件夹被其他程序占用（改名、删除时，主要在 Windows 上） | 写明文件夹被其他程序占用，操作失败 | 重试 |
| 路径过长（提醒） | 创建时检查路径长度，接近或超过上限（Windows 默认 260 个字符）时给出警告 | 缩短名称或换一个更短的资源库位置 |

- P0：有替代品的辅助工具自动回退（例如没有 pnpm 时改用 npm），并说明
  装上之后会更快：输出里一行，加工作区一条提示。
- P0：应用找不到已安装的工具时，可手动指定路径：设置“运行环境”表的每一行
  有“指定路径…”，缺环境的提示上也有“已经装了？指定路径…”。
- 模板选择器里，缺少工具的模板照常显示、照常可选（设计稿已确定）：副标题用
  警告色写“当前未安装”；已安装的语言类模板写“当前电脑上是 X”。
  副标题只按已有的检测结果显示，选择器不触发检测；还没有检测过的工具，副标题留空
  （首次启动不检查，创建过一次该类项目后就有结果了）。

<a id="prd-run"></a>
### 4.2 运行与实时结果

“实时”由**磁盘上的文件变化**驱动，因此智能体的修改和用户的修改效果一致。
自动保存默认开启，停止输入 1 秒后保存（与 VS Code 的默认延迟一致，避免
半句代码就触发重载）；设置里可选三档：延迟后保存、失去焦点时保存、关闭。

| 类型 | “实时”的含义 | 结果面板 |
| --- | --- | --- |
| 静态页面 | 任何改动都会刷新预览 | 页面 |
| 前端开发服务器 | 框架自带的热更新 | 页面 |
| 单文件脚本 | 保存后自动重新运行；代码有语法错误时不运行，保留上次输出并标为“过期” | 输出 |
| 服务 | 一律由应用重启（停止再启动，端口不变）；随后重发上一次请求 | 请求面板和日志 |

<a id="prd-run-ownership"></a>
**运行的归属**（负责人，2026-10-11）。每一次运行有一个“持有者”：

| 启动方式 | 持有者 | 关闭标签页 | 退出应用 |
| --- | --- | --- | --- |
| 在应用里打开标签页 | 这个标签页 | 停止 | 停止 |
| 通过命令行（包括智能体） | 命令行 | 不停止；标签页只是“查看” | 继续运行，由后台的管理进程照看 |

- P0：**标签页持有的运行**：打开标签页即启动；关闭标签页即立刻停止；退出应用
  全部停止。无需确认，因为停止不会丢失任何东西。标签页开着时也可以手动停止，
  状态为“已停止”，预览区显示“运行”按钮。
- P0：**命令行持有的运行**没有标签页。在应用里打开它的标签页只是“查看”：
  界面明确写出“由命令行启动，关闭标签页不会停止”（智能体启动的写出智能体
  名称），并提供两个操作：“改为由我管理”（之后关闭标签页即停止）和“停止”。
  它在 `runyard stop` 时停止，或在一段时间没有活动后自动停止（活动的判断见下一条）。
- P0：退出应用：macOS 上关闭窗口不退出应用；Windows 上关闭最后一个窗口即退出应用（不做托盘图标）。
  命令行持有的运行在退出后仍由管理进程照看。
<a id="prd-idle-stop"></a>
- P0：**空闲自动停止只针对命令行持有的运行**，否则智能体启动的服务会一直挂着；
  标签页持有的运行不做空闲停止。默认空闲 30 分钟后停止，可在设置里调整。
  下面四项里任何一项都算活动、让计时归零：进程有输出；项目里的文件有变化；有命令提到它
  （`run`、`logs`、`status <名称>`、请求面板）；端口上有已建立的连接。应用里有标签页在查看
  它不算活动。已知的不准之处：两次采样之间的一次短请求，如果服务没打日志，可能记不到。
- P0：资源库里没有“运行但不打开”：已停止的项目，主操作是“打开”（打开即运行）；
  运行中的项目，操作是“停止运行”。
<a id="prd-run-view"></a>
- P0：**运行视图**（右上角的“N 个运行中”，每个页面和工作区都保留这个入口）
  列出每个运行实例：项目名、模板、端口、已运行时长、来源（标签页，或命令行加
  智能体名称），命令行持有的写明“空闲后自动停止”；每行有“停止”，另有“全部
  停止”；点一行，有标签页的切过去，没有的打开它（即“查看”）。“运行中”的数量
  包含标签页持有和命令行持有两类。
<a id="prd-restore-tabs"></a>
- P0：重新打开应用时恢复上次的标签页，但只启动当前显示的那一个，其余的标签
  显示“已停止”，切过去时再启动，避免一次拉起一大批服务。
- P1：“在后台保持运行”，作为每个 playground 的显式选项，用于需要服务器
  在标签页关闭后继续存活的场景。
<a id="prd-close-tab-confirm"></a>
- 说明：核实后发现 CodeSandbox 的做法是闲置后休眠，并不是关闭即停止；
  关闭即停止的是 VS Code Dev Containers 这类本地工具。本产品按负责人的
  决定，标签页持有的运行关闭即停止；关闭运行中的标签页前弹窗确认并写明会停止运行，可选“不再提示”。
- P1：运行视图在一个折叠分组里列出本机上并非由 Runyard 启动的开发服务器，
  让用户看得见、可以手动停止。

<a id="prd-status-and-ports"></a>
**状态与端口**

- P0：任何时刻只显示一个状态（stopped、installing、starting、ready、
  reloading、crashed、failed，以及“缺少环境”），并附带解决该状态的操作。
  脚本没有 ready：运行时是“运行中”，跑完是“已结束”（显示退出码和耗时）。
<a id="prd-ports"></a>
- P0：**端口**（负责人，2026-10-11）。应用为每个 playground 分配一个端口并记下来，
  下次沿用；默认在 7100 到 7999 的范围内分配；启动时如果被占用，改用下一个空闲端口，并在界面上
  说明（显示占用者；被 Windows 保留的端口没有占用者，写“被 Windows 保留”）；
  模板和运行器不写死端口。脚本没有端口。
<a id="prd-stop"></a>
- P0：停止、重启、全部停止。停止整棵进程树（不只是主进程），并确认端口已释放。

<a id="prd-script-projects"></a>

<a id="prd-template-engineering"></a>
## 5. 模板工程化

- **模板**是一个文件夹：`template.json` 加 `files/`。它指定一个**运行器**，
  自身从不包含命令。变量是对所列文件中 `{{name}}` 的字面替换。没有钩子
  脚本，创建时不访问网络。
- **运行器**是一个 `runner.json`：detect、kind、needs、setup、run、ready、
  preview、watch、stop、actions。新增一种语言就是新增一个运行器文件。端口由
  应用分配并传入，运行器不写死端口。
- 运行器里的命令写成**参数数组，不经过 shell**（不写 `&&`、管道、`~`，`template lint` 对此报错）；
  `stop` 只写 `graceful` 或 `interrupt`，不写信号名；服务必须绑定 `127.0.0.1`。
- 两种格式都是 JSON，带 JSON Schema 和整数格式版本号。
<a id="prd-template-lint-test"></a>
- P0：`runyard template lint` 和 `runyard template test`。冒烟测试依次
  创建、安装、启动、等待就绪、修改入口文件并检查重载、停止，再检查没有
  残留的运行进程。它在 CI 中对每个 pull request 运行。
- P1：每周从上游脚手架重新生成，并自动提交 pull request；每晚跑一次完整
  测试；模板目录可在应用版本之间更新。
- 模板必须有具名维护者且冒烟测试通过才会被接受，连续 30 天测试不通过
  则从索引中移除。

<a id="prd-template-versions"></a>
### 5.1 模板的版本

版本号均为 2026-10-11 从 npm 和官方发布页核实（调研记录为本机归档，不在仓库内）。

- **不同版本就是不同的模板，在选择器里平铺展示**（负责人 2026-10-11 看过
  设计稿后确定）。不做“一张卡片上切换版本”的交互。例如“React 19 +
  TypeScript”和“React 18 + TypeScript”是并排的两个模板，模板标识分别是
  `react19` 和 `react18`；命令行写作 `runyard new react18`。
- 内置十一个模板；数量多了以后靠搜索和分类，选择器可滚动。
- **语言类模板只有一个，名称里直接写明需要的版本**，例如“Python（需要
  3.12 以上）”“Go（需要 1.22 以上）”，实际使用电脑上已装的版本。
- **同一框架最多保留两个版本的模板。** 服务端框架的旧版本必须仍在上游的安全维护期
  内；纯前端库的旧版本必须仍有相当的使用量。
- **版本退役只是从选择器里隐藏。** 用旧版本创建的 playground 自带锁文件，
  不受影响，继续可用。

<a id="prd-runtime-requirements"></a>
### 5.1.1 运行环境：所有语言同一套规则

负责人 2026-10-11 确定：Node、Python、Go、Java 等不是每个人都装了，所有
语言一视同仁，不为某一种语言做特殊处理。

1. **声明。** **每个模板都写明自己依赖的运行环境**：需要哪些工具、各自的
   版本范围（有上下限，不只是最低版本），以及安装方式。不依赖任何工具的
   模板（如静态页面）写明“无”。详见下面的“模板里怎么写”。
2. **检查。** 创建或打开项目时，检查这个项目需要的工具是否存在、版本是否
   满足。只查用得到的，不查别的。
3. **提示。** 缺少或版本不够时，说明缺什么、需要什么版本、当前是什么版本，
   并给出**当前操作系统对应的**安装方法。
4. **先提示，安装由用户发起。**（负责人，2026-10-11）应用不会悄悄安装任何
   东西，也不让工具自己悄悄下载（运行时关闭 uv 和 Go 自带的自动下载）。
   - **P0：只提示。** 说明缺什么，给出安装命令和官网链接，附“复制命令”
     “在终端中运行”“重新检测”。命令是否执行完全由用户决定。
   - **P1：在提示的基础上增加“安装”按钮。** 用户点了才在内置终端里执行，
     全程可见，可以取消；装完自动重新检测并继续启动。这一步要等安装脚本
     能按用户电脑的实际情况选对安装方式之后再开放。

**每个工具有一份定义**，包含三部分：

| 部分 | 内容 |
| --- | --- |
| 版本支持 | 应用认识这个工具的哪些版本，各模板在此基础上声明自己的版本范围 |
| 检测脚本 | 用什么命令判断工具是否存在、怎么读出版本号（如执行 `node --version`） |
| 安装脚本 | 按操作系统分开的安装命令，并按用户电脑的实际情况选择：已经在用版本管理工具（如 nvm）的，用它来装，避免装出第二套；否则用系统的软件安装工具；都没有时只给官网链接 |

- **一键安装只对应用内置的工具定义开放。** 第三方模板自带的安装脚本属于
  别人写的任意命令，只展示、不提供一键执行，由用户自己判断。
- 需要管理员密码的安装步骤，由终端照常向用户询问，应用不经手密码。

**安装方法按操作系统分别给出**，因为 macOS 和 Windows 的装法不同：

| 工具 | macOS | Windows |
| --- | --- | --- |
| Node | Homebrew 命令，或官网安装包 | `winget install --id OpenJS.NodeJS.LTS -e --source winget`，或官网安装包 |
| pnpm | Homebrew 命令，或官网安装方式 | `winget install --id pnpm.pnpm -e --source winget`，或官网安装方式 |
| Python | Homebrew 命令，或官网安装包 | `winget install --id Python.Python.3.13 -e --source winget`，或官网安装包 |
| uv | Homebrew 命令，或官网安装方式 | `winget install --id astral-sh.uv -e --source winget`，或官网安装方式 |
| Go | Homebrew 命令，或官网安装包 | `winget install --id GoLang.Go -e --source winget`，或官网安装包 |

- Homebrew 是 macOS 上常用的软件安装工具；winget 是 Windows 自带的软件安装工具；
  Scoop 是另一个常见的 Windows 安装工具。Java 暂时没有对应的 P0 模板，不在此表。
- Windows 上提示的优先级：用户已有的版本管理工具，其次 winget，其次 Scoop（winget 和 Scoop
  检测到才显示命令），最后是始终显示的官网链接。
- 每种工具都同时给出**官网下载链接**作为保底，因为用户不一定装了
  Homebrew。检测到系统里有对应的安装工具时，才显示命令。
- Linux 的安装方法同样按此结构预留。
- Windows 的命令来自技术设计 §7.4（包标识已核实存在；默认安装目录、`--source winget` 是否
  必要尚未核实）；macOS 的具体命令在设计阶段逐条核实后写入。

**模板里怎么写。** 每个模板的 `template.json` 里有一段 `requires`，逐个
列出依赖的工具和版本范围：

```json
"requires": {
  "node": { "version": ">=20.19 <27" },
  "pnpm": { "version": ">=10", "fallback": "npm" }
}
```

- **版本范围**写明下限和上限。下限是模板实际需要的最低版本；上限是维护者
  测试通过的最高主版本，超出时在工作区里给一条“未经测试”的提醒，而不是直接拦住。
- **安装方式**分两层。常见工具（Node、Python、Go、Java、pnpm、uv 等）的
  安装方法在应用里统一维护一份，按操作系统分开，这样十几个模板不必各抄
  一遍，更新时也只改一处。模板默认沿用这一份；有特殊要求的模板可以在
  自己的 `requires` 里另写安装方式，覆盖默认值。
- **校验命令会检查这一段**：`runyard template lint` 发现模板没有声明
  `requires`、版本范围写法不对、或用到了应用不认识又没给安装方式的工具，
  都判为不通过。冒烟测试会在声明范围的下限和上限版本上各跑一次。

<a id="prd-cli"></a>
## 6. CLI

`runyard new <template> [name] --run --json` 完成创建、启动、等待就绪，并
返回路径、URL 和日志游标。这一条命令就是要求 5。不给名称时，按 §4.1 自动命名
（模板标识加序号）。

<a id="prd-cli-commands"></a>
- P0：`new`、`run`、`stop`、`status`、`logs`、`rm`、`doctor`（`doctor --bundle` 导出诊断包）、
  `template list | show | save | lint | test`、`skill install`。
- P1：`prune`、`exec`、`open`、`screenshot`、`template add | update | remove`。
- P2：`runyard mcp`。
<a id="prd-cli-json"></a>
- 始终为非交互式。`--json` 只输出一个对象。错误带有错误码和提示，提示中
  写明下一步该执行的命令。对运行中的 playground 执行 `run` 会返回它本身，
  而不是再启动一个。
- 通过命令行启动的运行，持有者是命令行（见 §4.2）：在 `runyard stop` 时停止，
  或空闲一段时间后自动停止。
<a id="prd-cli-language"></a>
- **命令行的提示支持中文和英文，默认英文**（负责人 2026-10-12 决定）：错误、状态和进度行、`--help`
  都有英文和简体中文两份。默认是英文，在任何系统上都是，不自动跟随系统语言。切到中文有三种办法，
  优先级从高到低：单条命令加 `--lang zh-CN`；环境变量 `RUNYARD_LANG=zh-CN`；一次性设置
  `runyard config set lang zh-CN`。第一版支持的值是 `en` 和 `zh-CN`，不认识的值退回英文并提示一行。
  `--json` 的输出不受语言影响：字段名和错误码是稳定的英文，`message` 和 `hint` 永远是英文，智能体看错误码。
  桌面应用和命令行各自设置语言，互不影响。
<a id="prd-cli-distribution"></a>
- **第一版 CLI 只随桌面应用安装，不发 npm**（负责人 2026-10-12 决定）：设置里的“安装命令行工具”
  把它接到系统的 `PATH` 上，应用内置的终端里一定有 `runyard` 命令；从源码运行是给贡献者的方式。
  只有 `open` 和 `screenshot` 需要桌面应用。Windows 上命令行随 Windows 预览版一起提供。
<a id="prd-cli-clean-after"></a>
- 创建时默认已保留，带 `--clean-after 30d` 才开启自动清理。
<a id="prd-cli-creator"></a>
- playground 会记录创建者：种类（我或智能体）、智能体名称、创建时间、创建命令
  和备注。资源库用徽标标出智能体创建的 playground，写明是哪个智能体，并提供
  筛选。给智能体的 skill 里要求创建时带 `--note`。

## 7. 质量要求

<a id="prd-decisions"></a>
## 9. 决策

<a id="prd-decided-by-default"></a>
### 在此已定；如不同意请提出

1. **由一个管理进程掌管所有运行实例**，应用和 CLI 谁先需要就由谁启动。
   应用退出后，命令行持有的运行继续，由管理进程照看。这消除了“CLI 可独立工作”
   与“应用能看到一切”之间的冲突。
2. **Electron**、**MIT**、**macOS 为正式版，Windows 11 为预览版（Linux 只跑自动测试）**、**单窗口多标签页**（资源库固定在
   第一个，每个打开的 playground 一个标签页）。
3. **默认不自动删除；自动清理由用户逐个项目选择开启**（负责人，
   2026-10-11，先定为“绝不自动删除”，后在设计稿上改为可选的自动清理）。
   自动停止只针对命令行持有的运行（P0），不会丢失任何东西。
4. **Node 模板优先使用 pnpm，回退到 npm**，较慢但可用。
5. **先做十一个模板**（见 §5.2），而不是二十个；其余分批加入。
6. **运行器命令只随应用版本变更**；模板文件可在版本之间更新。
7. **官方模板内置在应用里，同时接受贡献。** 模板源文件先放在主仓库的独立
   目录中，格式稳定后拆成独立仓库；第三方模板不经官方收录，可作为“来源”
   自行添加。
8. **不内置任何语言的运行环境，也不代替用户安装。** 用本机已装的；缺的
   只提示并给出命令。

## 10. 风险

| 风险 | 应对 |
| --- | --- |
| 编辑器吞掉排期：Vue 和 Svelte 语法、依赖类型、worker 配置 | 在 M0 做技术验证；P0 仅限高亮加 TS/JS 智能提示 |
