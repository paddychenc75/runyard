# K2：输出走管道时，能否干净地停掉整棵进程树并释放端口

技术设计 §11.1 表里 K2 一行的验证。一次性代码，M0a 结束时删除。日期：2026-10-12。

## 结论（先看这里）

**设计成立，“运行的输出用管道、不用伪终端”（附录 A 第 1 行）不需要重开。**

- **macOS：进程组一次覆盖整棵树，够用。** 八个运行器在本机和 `macos-26` 上各 900 次停止，残留 0，端口最慢 99 ms 可重绑。不需要“按工作目录再扫一遍补杀”这条退路来杀进程；但 Next 退出时会另起一个脱离进程组、活不到 1 秒的遥测进程，改名和删除之前要等它走掉（见“边界情况”）。
- **Windows：`taskkill /T /F` 对八个运行器都够用。** 630 次停止残留 0，端口最慢 123 ms；另有 162 次放在“只观察”的 Job Object 里核对，Job 的成员表也是 0。没有哪个运行器必须靠 `runyard-job.exe`。
- **强制结束没有把项目弄坏。** 三个系统上“启动中途停、安装中途停、强制结束”之后的下一次启动和重装全部成功。唯一的副作用是 `go run` 留下临时目录，纯 JS 就能解决（见建议）。
- **`runyard-job.exe` 可行，而且比设计设想的多一样本事：** 管道不变、不用伪终端，它也能让 Windows 上的运行收到 Ctrl+C 优雅退出。它不是 K2 通过的前提，是否采用请负责人定（见“需要决定的一件事”）。
- **3 秒标准有一处要改：** 示例里 `graceMs: 3000` 与“停止后 3 秒内端口可重绑”相抵，建议默认 2000。

三条通过标准的判定在“对照通过标准”一节，带数字。

## 做了哪些实验

八个运行器：`static`、`vite`、`next`、`nuxt4`/`nuxt3`（同一个运行器的两个模板）、`node-ts`、`python`、`go`、`hono`。每个都是运行时写进临时目录的最小项目，命令是参数数组、不经过 shell，输出走管道，只绑定 `127.0.0.1`，同一个项目每次都用**同一个端口**（设计里重启时端口不变，这是最严的考法）。

| 场景 | 做法 | 每个运行器、每种办法的次数 |
| --- | --- | --- |
| 起停 | 启动 → 等 `GET /` 回 200 → 停止 | 50（对比用的办法 15，伪终端 5） |
| 请求进行中 | 就绪后开一个 10 秒才回的请求和一条空闲长连接，再停止 | 5（对比用的办法 3） |
| 启动中途停止 | 在典型就绪时间的 10%、30%、50%、70%、90% 处停止，然后马上正常启动一次 | 5 |
| 强制结束（POSIX） | 直接整组 SIGKILL，然后马上正常启动一次 | 10 |
| 中断信号（POSIX） | 用 SIGINT 代替 SIGTERM | 10 |
| 安装中途停止 | 新目录里 `pnpm install --prefer-offline`，在一次完整安装耗时的 25%、50%、75% 处停止；原样再装；再起停一次 | 3（有依赖的五个） |
| 进程树对比 | `pnpm exec vite`、`node --watch`、`uv run` 各起停 5 次 | 5 |
| 对照组 | `orphan`（中间进程退出，孙进程留在组里）、`escape`（孙进程另起会话）：用来证明查残留的手段查得出残留 | 3 |

设计里静态页面由管理进程自己托管、不起进程；这里既量了起一个 node 进程的替身（`static`），也量了进程内托管（`static-inproc`：关掉服务并断开所有连接，端口 0 到 2 ms 可重绑，200 次）。

**停止办法**

| 名字 | 系统 | 做法 |
| --- | --- | --- |
| `group` | POSIX | 子进程自成进程组；整组 SIGTERM，最多等 3000 ms，再整组 SIGKILL |
| `taskkill` | Windows | node 直接启动；`taskkill /PID <pid> /T /F` |
| `taskkill-obs` | Windows | 同上，但整棵树放在一个不带“关闭即杀”的 Job Object 里，只为拿 Job 的成员表当权威答案 |
| `job` | Windows | `runyard-job.exe` 建带“关闭即杀”的 Job Object；停止 = 结束这个辅助程序 |
| `job-ctrlc` | Windows | 辅助程序另开一个自己的隐藏控制台，停止时向它发 Ctrl+C，3000 ms 没退再结束整个 Job |
| `pty-ctrlc` | Windows | node-pty 1.1.0 的伪终端里写入 Ctrl+C。只为对比 |

**怎么查残留**（每次停止之后都查）：从启动起持续采样进程表，记下根进程的全部后代（进程号加启动时间）；给子进程的环境变量放一个唯一标记，后代都会继承，停止后在整台机器上找带这个标记的进程（macOS 用 `ps -E`，Linux 读 `/proc`）；找命令行或工作目录里出现临时目录的进程；试着重新绑定端口。Windows 读不到别的进程的环境变量和工作目录，所以另加了 `taskkill-obs` 和“端口绑不上时用 `netstat` 找监听者”。

**辅助程序用什么做的：** 170 行 C（`win/runyard-job.c`，含注释），在 `windows-2025` 上用镜像自带的 MinGW-w64 gcc 15.2.0 编译，18 432 字节，SHA-256 `1ebaa599…05ad4ae`（第 5 轮 light/b 任务的编译结果），只依赖 `KERNEL32.dll` 和系统自带的通用 C 运行库（`api-ms-win-crt-*`）。产品版本还需要什么见“建议”。

## 结果

完整的表在 `results/tables.md`，原始记录在 `results/*.json`。数字来自第 5 轮 CI（全部 20 个任务成功）和本机 Mac 的一次完整运行。

### 残留进程和端口

不含对照组。“停止次数”是所有场景加起来。

| 环境 | 办法 | 停止次数 | 有残留的次数 | 升级为强杀 | 端口可重绑 ms：中位 / p95 / 最大 | 超过 3 秒 |
| --- | --- | --- | --- | --- | --- | --- |
| 本机 Mac | `group` | 900 | 0 | 0 | 16 / 17 / 49 | 0 |
| `macos-26` | `group` | 900 | 0 | 0 | 16 / 21 / 99 | 0 |
| `ubuntu-latest` | `group` | 900 | 0 | 0 | 15 / 18 / 233 | 0 |
| `windows-2025` | `taskkill` | 630 | 0 | — | 68 / 89 / 123 | 0 |
| `windows-2025` | `taskkill-obs` | 162 | 0（Job 成员表也是 0） | — | 67 / 86 / 96 | 0 |
| `windows-2025` | `job` | 630 | 0 | — | 23 / 31 / 33 | 0 |
| `windows-2025` | `job-ctrlc` | 162 | 0 | 6 | 24 / 517 / 534 | 0 |
| `windows-2025` | `pty-ctrlc` | 72 | 0 | 0 | 24 / 508 / 528 | 0 |

端口每 15 ms 试绑一次，所以 16 ms 上下就是“立刻”。500 ms 那一档全是 Python：它收到 Ctrl+C 后要等自己的轮询周期。按运行器分开的数字见 `results/tables.md` 的 A、B 两张表，没有哪一格超过 233 ms。

管道：所有运行器的停止里，根进程退出后 1 秒内都收到了 `close`，没有后代占着管道。只有对照组 `escape` 每次都占着。

### 停止之后的下一次启动

| 场景 | 系统 | 结果 |
| --- | --- | --- |
| 启动中途停止后再启动 | 三个系统，全部运行器和办法 | 每格 5/5 成功 |
| 整组 SIGKILL 后再启动 | macOS、Linux，九个项目 | 每格 10/10 成功 |
| 每次起停都是强制结束 | Windows，`taskkill` 和 `job` | 每个运行器 49/49 次“上一次被强杀后的启动”成功 |
| 安装中途停止后原样重装 | 三个系统，vite、next、nuxt4、nuxt3、hono | 每格 3/3 成功，重装后启动 3/3 成功 |

`.next`、`.nuxt`、`node_modules/.vite`、`node_modules/.cache` 被强杀后都没有挡住下一次启动。重装时没有设 `CI` 变量，pnpm 没有停在确认提示上。安装中途停止时 `node_modules` 有时已经建了一半（本机 15 次里 7 次），重装照样成功。

**没有验证：** Python 虚拟环境（P0 的 Python 模板没有第三方依赖，不建虚拟环境）；装一个真正大的依赖树到一半；用户自己的 pnpm 仓库被强杀时会不会坏（实验用的是临时仓库）。

### 每个运行器起了哪些进程

| 命令 | macOS、Linux | Windows（另有一个 `conhost.exe`） |
| --- | --- | --- |
| `node node_modules/vite/bin/vite.js` | 1 个 | 1 个 |
| `pnpm exec vite` | 3 个：pnpm → vite，外加 pnpm 的一个看门 `sh` | **4 层 4 个**：`cmd.exe` → node（pnpm）→ `cmd.exe` → node（vite） |
| `next dev` | 2 个：next → `start-server.js`；退出时另起 `detached-flush.js` | 2 个 |
| `nuxt dev`（4 和 3 相同） | 4 个：nuxt → esbuild 服务、两个 node 子进程 | 4 个 |
| `node main.ts`、Hono | 1 个 | 1 个 |
| `node --watch main.ts` | 2 个 | 2 个 |
| `python -u main.py` | 1 个 | 1 个 |
| `uv run main.py` | 2 个：uv → python | 2 个 |
| `go run .` | 2 个：go → 编译出的程序（编译期间最多 10 个） | 2 个（编译期间最多 6 个） |

**“直接用 node 跑 Vite 的入口、不经过 pnpm”确实让树变简单：** Windows 上从 4 层降到 1 层，还省掉两层 `cmd.exe`。两种写法用 `taskkill` 和 `job` 都停得干净（各 5 次，残留 0）。

`go run` 没有成为孤儿问题：POSIX 上子程序和 `go` 在同一个进程组；Windows 上 `taskkill /T` 顺着父进程号找得到它（50 次停止残留 0，Job 成员表核对 15 次也是 0）。

### 伪终端加 Ctrl+C 比强制结束好多少

| 比较 | `taskkill`（强制） | `job-ctrlc`（管道，Ctrl+C） | `pty-ctrlc`（伪终端，Ctrl+C） |
| --- | --- | --- | --- |
| 端口可重绑，中位 | 59 到 86 ms | 18 到 28 ms（Python 517） | 17 到 31 ms（Python 523） |
| 根进程退出，中位 | 59 到 91 ms | 9 到 281 ms（Python 513） | 1010 到 1530 ms（node-pty 报告退出要晚约 1 秒） |
| 程序有没有机会收尾 | 没有，退出码一律 1 | 有：Next、Nuxt 退出码 0，`go run` 删掉了临时目录 | 有，同左 |
| 残留 | 0 | 0 | 0 |
| 代价 | 无 | 一个 18 KB 的 exe | 原生模块进管理进程；每开一次伪终端多一个 `conhost.exe`，到测试程序结束时还在（一个任务里累计 8 到 46 个） |

也就是说：**强制结束在这八个运行器上除了 `go run` 的临时目录之外没有可见的坏处**；而优雅退出的好处，不用伪终端也拿得到。伪终端只测了每个运行器 8 次。

`job-ctrlc` 有 6 次 Ctrl+C 之后 3 秒没退（nuxt4 15 次里 5 次、nuxt3 15 次里 1 次），升级为结束整个 Job，根进程 3.0 到 3.3 秒才退出。这 6 次端口其实 30 ms 就放开了，但说明“等满 `graceMs` 再强杀”在 3000 ms 时会顶到 3 秒线。

### 对照组说明了什么

- `escape`（孙进程另起会话、中间进程退出）：POSIX 的进程组**每次都漏**（9/9），端口一直被占，管道也被占；`taskkill /T /F` **每次都漏**（3/3），靠进程树或 `netstat` 才找到；`job` **每次都杀掉**（3/3，17 到 19 ms 端口可用）；伪终端也漏（3/3）。
- `orphan`：POSIX 上孙进程还在组里，3/3 杀掉。Windows 上它在停止之前就自己没了：node 的非 detached 子进程会随 node 父进程一起结束【推断：libuv 把它们放进了一个“关闭即杀”的 Job；没有读源码核实】。这有两个后果：node 写的工具链在 Windows 上天然不容易留孤儿；**管理进程自己如果崩了，它直接启动的运行在 Windows 上会跟着全部结束**，macOS 上不会。

## 需要决定的一件事：`runyard-job.exe` 做不做

设计写的是“如果 K2 证明 `taskkill /T /F` 加端口复查已经够了，这个辅助程序就不做”。按这句话，**证据是够了**：八个运行器 `taskkill` 全部通过。

但实验也量出了它的三样好处，供负责人权衡：

1. 管道不变就能优雅退出（上表），`go run` 不再留临时目录，Next、Nuxt 有机会正常收尾。
2. 用户代码自己另起后台进程时，`taskkill` 漏、它不漏（对照组 3/3 对 0/3）。
3. 不依赖“父进程号”。Windows 的父进程号在父进程死后不变，进程号又很快被复用，凭它认亲会认错。**这次的测试程序自己就栽在这上面**（见“一次事故”）。`taskkill /T` 也是顺着父进程号找的，它是否做了防复用的核对，本次没有查清。

代价：多一个要编译、要随应用分发的未签名 exe（会不会被杀毒软件拦，K14 看）；它自己也有一处竞态要处理（见“边界情况”第 5 条）。

**建议：** M1 先用 `taskkill /T /F` 加端口复查（纯 JS，已满足标准）；辅助程序列为 Windows 预览版（MW）之前的增强项，等 K14 看过杀毒软件的反应再定。这不改变任何核心设计。

## 建议的停止算法

```
停止(run, mode, graceMs):                      # 两个系统都只等 exit 事件，不等管道 close
  若 run.kind 是 static：关掉进程内的服务并断开所有连接；结束

  POSIX（启动时 detached，子进程自成进程组，组号 = 根进程号）：
    信号 = mode 为 interrupt 时 SIGINT，否则 SIGTERM
    kill(-组号, 信号)
    每 10 ms 看一次 kill(-组号, 0)，直到报 ESRCH（组空了）或过了 graceMs
    组还在：kill(-组号, SIGKILL)，再等组空（上限 5 秒）
    试绑端口确认可用；销毁输出管道
    改名、删除之前：在整台机器上找带本次运行标记的进程，等它们走掉（上限 2 秒），还在就结束它们

  Windows 第一版（没有辅助程序）：
    核对根进程还活着，而且创建时间和启动时记下的一致（防进程号被复用）
    taskkill /PID <根进程号> /T /F
    等根进程的 exit 事件（上限 5 秒）
    试绑端口；绑不上：netstat 找出监听者，核对它是本次运行启动之后创建的，结束它，记一条日志
    销毁输出管道

  Windows 有辅助程序时：
    向辅助程序的标准输入写 "ctrlc"；等它退出，最多 graceMs
    没退：写 "kill"（TerminateJobObject）；再等 2 秒；还不退才直接结束辅助程序
    试绑端口；销毁输出管道
```

## 生产代码必须处理的边界情况

1. **不要等 `close`，等 `exit`。** 后代拿着管道写端时 `close` 不来（对照组每次如此）。停止确认后主动销毁管道。
2. **Next 退出时另起一个脱离进程组的遥测进程**（`next/dist/telemetry/detached-flush.js`，设了 `NEXT_TELEMETRY_DISABLED=1` 仍然会起）。它不占端口，但工作目录在项目里，停止后还活一小会儿：中位 0.18 到 0.73 秒，最长 0.95 秒（本机 85 次、`macos-26` 84 次、Linux 88 次都看到了）。不影响“停止”，影响紧接着的改名和删除。强制结束时不会有它。
3. **`go run` 被 SIGTERM、SIGKILL 或 `taskkill` 结束时，每次留下一个 `go-build*` 临时目录**（三个系统都是，每次 1 个）；SIGINT 或 Ctrl+C 时一个不留。
4. **Windows 上认后代必须核对创建时间**：孩子的创建时间不早于父进程；结束任何进程之前核对它是本次运行启动之后创建的。只凭父进程号会杀错。
5. **辅助程序刚启动就被结束会漏掉子进程。** 第 4 轮里有一次在启动后 13 ms 结束辅助程序，子进程已经建出来但还没放进 Job，结果 `python.exe` 留下了（5 次里 1 次；记录在 `results/round4/windows-2025-light-b.json`）。产品版本要么用创建时就指定 Job 的系统接口（`PROC_THREAD_ATTRIBUTE_JOB_LIST`），要么停止一律走标准输入的指令、不直接结束辅助程序。
6. **“忽略 Ctrl+C”会从父进程继承。** 第 1 轮里辅助程序发出的 Ctrl+C 没人理，因为 CI 的执行器让整棵树继承了这个属性；辅助程序里先 `SetConsoleCtrlHandler(NULL, FALSE)` 清掉之后才生效（第 2 轮起）。管理进程是脱钩启动的，很可能也带着这个属性。
7. **Ctrl+C 只能发给“同一个控制台”上的进程。** 辅助程序必须先拿到自己的控制台再发，拿不到就不发，否则会打到调用方。脱离了控制台的后代收不到（对照组：等了 3 秒后由 Job 结束）。
8. **端口一直绑不上时不要死等。** 实验里上限是 8 秒；到时按“原端口被占用”处理（§4.5 已有这条路）。
9. **启动后立刻停止**（进程还没来得及建子进程、建组）三个系统都测过，没有问题；但辅助程序那条路有第 5 条的竞态。
10. **Python 标准库的 `http.server` 在 `macos-26` 上启动要多等 35 秒**（它在绑定时做一次反向域名查询）。与停止无关，但 Python 的服务类模板如果用它会撞上。

## 一次事故（测试程序的错，写在这里是因为它本身是一条证据）

第 2 轮里 `windows-2025 / nuxt3 / a` 任务在第 44 次起停后，整台 CI 虚拟机再也起不了新进程（退出码 `0xC0000142`），第 3 轮同一个任务直接挂死。原因在测试程序：它凭“父进程号”把进程认作本次运行的后代，而我们树上的某个进程恰好拿到了一个早已退出的系统进程用过的进程号，于是 `csrss.exe`、`winlogon.exe`、`fontdrvhost.exe`、`dwm.exe` 被当成后代，又在“兜底清理”里被当成残留去结束。记录见第 2 轮该任务的日志（“残留=csrss.exe、winlogon.exe…”那一行）。

修法：认后代时核对创建时间，清理时只结束本次运行启动之后创建、且程序名在清单里的进程。修完之后第 4、5 轮这个任务各 50 次全部干净。**受影响的只有 GitHub 的一次性虚拟机，没有碰到本机。** 根因是按上面推断的，没有在出事的机器上进一步取证；第 3 轮那次挂死没有留下日志，是否同一原因未核实。

## 需要在负责人的 Windows 真机上复核

1. 普通用户、Windows 11、杀毒开着：`taskkill /T /F` 对 vite、next、nuxt、`go run` 各起停十来次，看残留和端口（CI 是管理员加 Server 版）。
2. 强杀之后马上改名、删除项目文件夹（K9b 的内容），尤其是 Next 和 Nuxt。
3. `go run` 在杀毒开着时每次生成新程序的首次扫描耗时，会不会让“启动中途停止”更容易留下东西。
4. 若采用辅助程序：未签名的 `runyard-job.exe` 会不会被拦（K14）；它另开的控制台会不会闪一下黑窗口（CI 上没有桌面，看不到）；从 Windows Terminal、VS Code 终端启动的管理进程下，Ctrl+C 是否仍然只打到目标树。
5. arm64 的 Windows 没有测。
