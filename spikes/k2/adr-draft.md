# NNNN. 停止运行：进程组和 taskkill，输出仍走管道

状态：提议中

日期：2026-10-12

来源：技术设计 §4.3、§4.4、§7.2 第 2、3 行和表后“Job Object 辅助程序的形态”、§11.1 K2 行、附录 A 第 1 行；K2 技术验证

## 背景

运行的输出用管道接收，不用伪终端（附录 A 第 1 行）。这条裁决的代价是 Windows 上第一版只能强制结束，当时没有核实三件事：整棵进程树停不停得干净、端口多久能重新绑定、强制结束会不会留下坏的锁文件让下一次启动失败。K2 在本机 Mac 和 GitHub 的 macOS、Windows、Linux 机器上，对八个运行器各起停 50 次，另做了请求进行中、启动中途、安装中途停止，把这三件事量了出来。

## 决定

维持“输出走管道”。macOS 上每次运行自成一个进程组，停止时整组发终止信号，等 `graceMs`，再整组强制结束。Windows 第一版用 `taskkill /T /F` 结束整棵树，再试绑端口复查，绑不上时找出监听者结束它。`runyard-job.exe` 第一版不做，保留为 Windows 预览版之前的增强项，等 K14 看过未签名 exe 的情况再定。

依据（K2 实测）：macOS 1800 次停止、Windows `taskkill` 630 次停止，残留进程 0；另 162 次用 Job Object 的成员表核对也是 0。端口最慢 99 ms（macOS）和 123 ms（Windows）可重新绑定，标准是 3 秒。强制结束之后的下一次启动、安装中途停止之后的重装，三个系统全部成功。

## 后果

- 停止只等进程的退出事件，不等输出管道关闭；确认停止后主动销毁管道。
- `graceMs` 默认 2000，不是 3000：升级为强制结束时停止会拖到 `graceMs` 之后，3000 顶到 3 秒线。
- Windows 上结束任何进程之前核对它的创建时间：父进程号在父进程死后不变、进程号很快被复用，只凭它会杀错。验证用的测试程序就因此弄坏过一台 CI 机器。
- 每次运行的环境变量带一个运行标记。macOS 上改名、删除之前用它在全机找一遍，等带标记的进程走掉：Next 退出时会另起一个脱离进程组的进程，最长活了 0.95 秒。
- Go 的运行器在 macOS 上用中断信号停止；管理进程给每次运行单独设 `GOTMPDIR` 并在停止后删除。否则 `go run` 每次被结束都留下一个临时目录。
- 运行器的启动命令继续直接用 `node` 跑入口文件：Windows 上 `pnpm exec vite` 是 4 层进程，直接跑是 1 层。
- 以后若做 `runyard-job.exe`：用创建时指定 Job 的系统接口；停止走标准输入的指令，不直接结束它；发 Ctrl+C 之前自己开控制台，并清掉继承来的“忽略 Ctrl+C”。K2 已验证这样做能在管道下让 Windows 上的运行优雅退出。
- Windows 的数字来自 Windows Server 2025 的 CI 机器。发 Windows 预览版之前要在真机上以普通用户复核。

## 被否的方案

- 运行改走伪终端，靠它在 Windows 上发 Ctrl+C：强制结束没有弄坏任何一个运行器的项目，伪终端要把原生模块带进管理进程，收益换不回这个代价；需要优雅退出时辅助程序在管道下就能做到。
- 第一版就做 `runyard-job.exe`：`taskkill` 已满足三条标准；辅助程序多一个未签名的 exe，杀毒软件的反应还没有看（K14）。
- macOS 上停止后按工作目录补杀：1800 次停止没有一次需要；只保留“改名、删除前等带标记的进程走掉”。
- 只凭父进程号找后代来清理残留：进程号复用时会认错，见“后果”第三条。
