# 0005. 运行输出走管道，日志存原始字节、读取时清洗

状态：提议中

日期：2026-10-12

来源：技术设计 §4.5、§7.2 第 13 行、§11.1 K4、附录 A 第 1 行

## 背景

附录 A 第 1 行裁决运行输出走管道、不用伪终端，代价是 Windows 上输出可能带控制字符、中文乱码、被整块延迟。K4 在 GitHub 的三个系统运行器上用 Vite 8.3.1、Next 16.3.6、Node+TS、Python 3.12 和 3.14、uv、Go 1.26、pnpm 11 实测：Vite、Next 的报错代码框自带颜色，任何环境变量和参数都去不掉；Python 在非 UTF-8 的 ANSI 代码页下写中文会直接崩溃，默认还会把输出攒成整块（强杀时丢光）；Node、Go 无此问题。真实中文 Windows 11（代码页 936）未测。

## 决定

继续走管道。日志文件和内存里存原始字节；`runyard logs` 和界面的纯文本由清洗规则生成：按 0x0A 切行；去行尾 CR；每行先严格 UTF-8、失败则按 GB18030 解码；去 BOM；`ESC[1G` 当回车；剥 OSC、DCS 等、CSI、`ESC` 加一字符；行内多个 `\r` 只留最后一段；删剩余 C0（保留制表符）、DEL、C1；纯控制序列的行丢弃。所有系统给运行加 `PYTHONUTF8=1`、`PYTHONUNBUFFERED=1`、`NEXT_TELEMETRY_DISABLED=1`；颜色沿用“强制颜色”。

## 后果

- 清洗规则是 `@runyard/core` 里一个带测试的函数，用 K4 的自检用例和批量用例作测试数据；
- 运行器环境变量表里加 `PYTHONUNBUFFERED=1`；模板说明写明“Vite、Next 的错误代码框颜色去不掉”和“`--no-color` 不可用（会报错退出）”；
- 不设 `CI=1`；`pnpm install` 不用 `--reporter=silent`；
- 两路输出按到达顺序合并，紧凑写入时跨管道顺序无法保证，文档不承诺严格顺序；
- 进入 M1 前在中文 Windows 11 真机上复核编码（K4 未覆盖的部分）。

## 被否的方案

- 伪终端：要把 node-pty 带进管理进程和命令行，且 Windows 的伪终端改写输出（附录 A 第 1 行）。
- 只靠 `NO_COLOR` 保证日志干净：Vite、Next 的原生报错框不认，实测仍剩颜色码。
- 只在 Windows 上加 `PYTHONUTF8`：缓冲问题在三个系统上都存在，统一加更简单。
